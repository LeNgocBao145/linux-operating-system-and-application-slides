01 — Motivation

The Problem

Modern Linux systems run many services — and they don't announce failure politely.

  • Servers, databases, web apps, network devices — all running in parallel
  • CPU, memory, disk, network, and processes drift silently over time
  • Failures often happen before a single user reports them
Question: how does an admin know something is wrong — before the user does?

01 — Motivation

What is Zabbix?

An open-source monitoring and alerting platform.

  • Collects metrics from hosts and services
  • Stores historical performance data
  • Displays dashboards and graphs
  • Raises problems when thresholds are crossed
  • Notifies people when something breaks

02 — Terminology

Core Terms

The vocabulary that everything else is built from.

TermMeaning
Zabbix ServerThe central component that collects metrics from agents, evaluates triggers, stores data, and manages configuration
AgentLightweight software installed on monitored hosts that collects local system metrics and sends them to the server
FrontendWeb-based GUI for viewing dashboards, graphs, managing configuration, and accessing alerts
ItemA single metric or data point that Zabbix collects, e.g. CPU usage, memory, disk space, or process count
TriggerA condition (threshold rule) that fires when an item's value crosses a boundary — transforms raw metrics into problems
ProblemA visible alert in the frontend created when a trigger fires; shown in dashboards and sent to users
TemplateReusable collection of items, triggers, graphs, and discovery rules that can be applied to multiple hosts

Discovery Types

Three ways Zabbix finds things to monitor.

FeatureWhat it discovers
Network discoveryHosts/services in an IP range
AutoregistrationActive agents that announce themselves
Low-level discovery (LLD)Things inside a host: filesystems, interfaces, nginx processes, etc.
Network discovery finds the host. LLD creates items/triggers inside templates.

04 — Demo

Trigger Demo: High CPU

Use CPU stress for a predictable PROBLEM event.

Trigger expression
min(/linux-client/system.cpu.util,30s)>80
Generate load
stress-ng --cpu "$(nproc)" --cpu-load 100 --timeout 90s
Why CPU instead of stopping nginx? Stable item, simple trigger, reliable alert — and nginx's LLD-based process triggers can be disabled by design.

05 — Positioning

Alternative: Prometheus + Grafana

Two philosophies for the same underlying job.

Zabbix

  • All-in-one monitoring platform
  • Strong host/service templates
  • GUI-heavy configuration
  • Good for classic infrastructure
  • Built-in problems/actions

Prometheus + Grafana

  • Metrics database + dashboard stack
  • Strong cloud-native metrics model
  • Config/query-heavy workflow
  • Good for Kubernetes/app metrics
  • Alertmanager is separate

06 — Wrap-up

Common Mistakes

Three easy ways to trip up during setup or demo.

  1. Confusing network discovery with LLD — network discovery finds hosts; LLD discovers entities inside hosts/templates.
  2. Using slow trigger windows in a short demo — use short intervals for classroom demonstration.
  3. Stopping the wrong thing — stopping the agent proves host unreachable; CPU stress proves threshold-based alerting; nginx dashboard proves service metrics.

06 — Wrap-up

Key Takeaways

  • Zabbix collects metrics using agents, templates and items.
  • Triggers turn metric values into visible problems.
  • Network discovery can automatically add hosts and link templates.
  • Dashboards make metrics understandable.
  • For this demo: nginx shows monitoring, CPU stress shows alerting.

Q&A

Q: Is active check the same as push?
Mostly — active agents first request their check list from the server, then send collected values later.
Q: Is network discovery the same as LLD?
No. Network discovery finds hosts. LLD discovers entities inside a host/template.
Q: Why use CPU stress for alerting?
It is deterministic and easy to recover from during a short demo.
