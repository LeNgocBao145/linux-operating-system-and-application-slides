Log Cơ Bản
4 / 37

Log là dấu vết của hệ thống

Công cụ cũ

  • cat, tail, grep
  • journalctl với systemd

  • Phải SSH vào từng máy

Nginx Logs

Nginx: ghi log ra file thật

# nginx/logging.conf
access_log /var/log/custom-nginx/access.log combined;

# docker-compose.yml
nginx:
  image: nginx:latest
  volumes:
    - nginx_logs:/var/log/custom-nginx
    - ./nginx/logging.conf:/etc/nginx/conf.d/logging.conf:ro

Image Nginx chính thức thường trỏ log ra /dev/stdout; mount sai đường dẫn có thể khiến Filebeat không đọc được file thật.

Pipeline
19 / 37

Logstash: input & output dùng chung

# 00-input.conf
input { beats { port => 5044 } }
# 90-output.conf
output {
  elasticsearch {
    hosts => ["http://elasticsearch:9200"]
    index => "%{[fields][service]}-logs-%{+YYYY.MM.dd}"
  }
}

Thêm service mới chỉ cần thêm file filter mới; output vẫn đặt tên index động theo fields.service.

Grok Filter là gì?

Cú pháp

%{PATTERN:tên_field}

Phần chữ hoa là pattern có sẵn; phần sau dấu : là field mới.

Giá trị

Tách một dòng text dài thành IP, timestamp, status, bytes, service...

grok { match => { "message" => "%{COMBINEDAPACHELOG}" } }

Custom Grok
22 / 37

Tự viết pattern cho app Python

Log gốc:
2026-07-23T16:41:28+0700 WARNING service=order-api message=Order processing exceeded latency threshold

Grok pattern:
"^%{TIMESTAMP_ISO8601:log_timestamp} %{LOGLEVEL:app_log_level} service=%{NOTSPACE:app_service} message=%{GREEDYDATA:app_message}$"

Kết quả:
log_timestamp: 2026-07-23T16:41:28+0700
app_log_level: WARNING
app_service:   order-api
app_message:   Order processing exceeded latency threshold
Mistakes
23 / 37

Lỗi thường gặp

Version lệch

Elasticsearch, Kibana, Logstash, Filebeat không cùng version.

Log là symlink

Nginx/Apache trong container ghi ra /dev/stdout, không phải file thật.

Restart chưa đủ

Sửa config nhưng không --force-recreate, container vẫn dùng config cũ.

Quên data view

Dữ liệu đã vào Elasticsearch nhưng Kibana vẫn “không thấy”.

Best Practices
24 / 37

Best practices khi dựng demo ELK

Khóa version

Dùng cùng một version cho Elasticsearch, Kibana, Logstash và Filebeat.

Đọc log thật

Kiểm tra docker compose logs -f <service> trước khi đoán lỗi ở đâu.

Tách pipeline

Đặt số thứ tự file Logstash để input đọc trước, filter ở giữa, output sau cùng.

Mở rộng bằng field

Dùng fields.service và index động để thêm service mà không sửa output.

Chỉ tắt bảo mật cho phạm vi demo/học tập; production cần bật lại các lớp xác thực và giới hạn mạng.

Logstash Security
25 / 37

Bảo mật Logstash

Rủi ro của demo

  • xpack.security.enabled=false
  • Port 5044 mở cho mọi nguồn
  • Có thể bị gửi log giả hoặc gây nhiễu dữ liệu
input {
  beats {
    port => 5044
    ssl_enabled => true
    ssl_client_authentication => "required"
    ssl_certificate_authorities => ["/certs/ca.crt"]
    ssl_certificate => "/certs/logstash.crt"
    ssl_key => "/certs/logstash.key"
  }
}

Hai lớp nên có: firewall/Security Group chỉ cho IP nguồn tin cậy, và mutual TLS để Filebeat phải trình chứng chỉ hợp lệ.

Khi nào nên dùng ELK?

ELK mạnh, nhưng không miễn phí theo nghĩa vận hành: nó cần RAM, đĩa và người chăm hệ thống.

Loki

Giải pháp thay thế: Grafana Loki

Đánh indexMọi field sau khi Grok táchChỉ vài nhãn: job, host, env

Khác biệt chính: ELK trả giá trước bằng index nhiều field; Loki tiết kiệm hơn nhưng parse sâu ở thời điểm query.

Label vs Index
29 / 37

Cùng một dòng log, hai cách lưu

203.0.113.45 - - [07/Aug/2026:04:40:12 +0700] "GET /products/38 HTTP/1.1" 404 512
198.51.100.9 - - [07/Aug/2026:04:40:13 +0700] "GET /products/91 HTTP/1.1" 404 498

Loki lưu

Nhãn {job="nginx", host="web-01", env="prod"} + nguyên hai dòng trên, nén lại. Hết.

Không biết 404 là status, không biết 203.0.113.45 là IP.

ELK lưu

Grok tách rồi index từng field: clientip, verb, request, response, bytes, @timestamp.

Tra field nào cũng có sẵn danh sách để nhảy tới.

Ranh giới: biết trước chỗ cần tìm (máy nào, giờ nào) → nhãn là đủ, phần còn lại grep. Phải quét cả đống để tìm ra chỗ → cần index field.

LogQL
30 / 37

Chỉ có nhãn thì truy vấn kiểu gì?

{job="nginx", env="prod"}      # dùng index để chọn khối dữ liệu
  |= "404"                     # grep trên text gốc vừa đọc lên
  | pattern "<ip> - - <_> \"<method> <path> <_>\" <status> <bytes>"
  | status = "404"             # tách field ngay lúc query

Quy tắc: nhãn chỉ dành cho thứ có ít giá trị như service, host, env. Không đặt nhãn clientip hoặc user_id vì cardinality cao sẽ làm Loki rất chậm.

ELK vs Loki
31 / 37

Chọn Loki thay ELK: được gì, mất gì

Được

  • Log để thẳng trên S3 — rẻ hơn ổ SSD vài lần
  • Nhẹ RAM, vì không index mọi field
  • Ít thành phần: một dịch vụ + object storage, không cần database

Mất

  • Thống kê theo field chậm — mỗi lần chạy phải đọc lại dữ liệu thô
  • Mỗi giá trị nhãn là một file riêng, nên đặt nhãn theo IP là sập; ELK index IP thì bình thường
  • Người viết query phải tự lo thứ tự cho nhanh
Graylog
32 / 37

Graylog: khai một cái nhóm, log tự vào

Trên giao diện Graylog, bạn tạo một nhóm log có tên — điều kiện và cài đặt nằm chung một chỗ.

Nhóm  "Lỗi web"
  điều kiện :  máy = web-*   và   status >= 400
  giữ       :  7 ngày rồi xoá
  ai xem    :  nhóm Web
  báo động  :  > 100 dòng/phút  →  Slack

Dòng log lúc nãy khớp điều kiện, nên trước khi ghi xuống OpenSearch nó đã được xếp vào nhóm này — và tự nhận luôn ba cài đặt còn lại.

ELK làm được cả ba, nhưng ở ba chỗ rời nhau: điều kiện viết trong Logstash, xoá log cũ khai trong ILM của Elasticsearch, phân quyền cấu hình trong Kibana.

ELK vs Graylog
33 / 37

Chọn Graylog thay ELK: được gì, mất gì

Được

  • Nhóm log gắn liền quyền xem, thời gian giữ và cảnh báo — khai một chỗ
  • Sửa luật tách field trên web, dán thử một dòng log xem trước khi lưu

Mất

  • Thêm một database phải lo sao lưu — mất MongoDB là mất hết cấu hình; Kibana chết thì bật lại là xong
  • Khoá vào OpenSearch; từ bản 6 bỏ hỗ trợ Elasticsearch
  • Vẽ biểu đồ và kho dashboard dựng sẵn thua Kibana

Chọn Graylog khi nhiều nhóm dùng chung một hệ thống log, mỗi nhóm chỉ được xem phần của mình. Nói thẳng: Graylog là lựa chọn lúc bắt đầu, không phải lúc đã chạy.
