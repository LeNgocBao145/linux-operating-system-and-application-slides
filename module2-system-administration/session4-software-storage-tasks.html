Slide 3 — Theory

apt & dpkg — Package Management

# update package index
$ apt update
$ apt upgrade # upgrade all
$ apt full-upgrade # + remove old deps

# install / remove
$ apt install nginx
$ apt remove nginx # keep config
$ apt purge nginx # remove config too
$ apt autoremove # clean orphans

# search and inspect
$ apt search nginx
$ apt show nginx
$ dpkg -l # list all installed
$ dpkg -L nginx # list package files
apt vs dpkg: apt handles dependencies automatically. dpkg is the lower-level tool — use it to install .deb files directly or inspect installed packages.
Version pinning — never accidentally upgrade
# pin nginx to current version
$ apt-mark hold nginx

# verify
$ apt-mark showhold
nginx

# unpin when ready to upgrade
$ apt-mark unhold nginx

# install specific version
$ apt install nginx=1.24.0-1
Production rule: Always pin critical services (nginx, postgresql, docker) before running apt upgrade. Unplanned upgrades break things.
Slide 4 — Theory

PPAs & Build from Source

PPA — Personal Package Archive
# add a PPA (e.g. newer PHP)
$ add-apt-repository ppa:ondrej/php
$ apt update
$ apt install php8.3

# remove a PPA
$ add-apt-repository --remove ppa:ondrej/php

# manual source entry
# /etc/apt/sources.list.d/nginx.list:
deb https://nginx.org/packages/ubuntu jammy nginx
Trust PPAs carefully. Adding a PPA grants that maintainer the ability to push packages to your system. Use official or well-known PPAs only.
Build from source — the classic way
# install build tools first
$ apt install build-essential

# download + extract source
$ wget https://example.com/app-1.0.tar.gz
$ tar xzf app-1.0.tar.gz
$ cd app-1.0/

# configure → compile → install
$ ./configure --prefix=/usr/local
$ make -j$(nproc)
$ sudo make install
./configure checks system dependencies and generates a Makefile. Always check ./configure --help for available options before building.
Slide 5 — Theory

Partitions, Format & Mount

# inspect disks
$ lsblk # tree view
$ fdisk -l # partition table
$ df -h # disk usage

# partition a new disk
$ fdisk /dev/sdb # interactive
# n → new partition
# w → write and exit

# format
$ mkfs.ext4 /dev/sdb1
$ mkfs.xfs /dev/sdb1

# mount manually
$ mkdir -p /mnt/data
$ mount /dev/sdb1 /mnt/data
$ umount /mnt/data
/etc/fstab — persistent mounts
# device mountpoint fs options dump pass
/dev/sdb1 /mnt/data ext4 defaults,nofail 0 2
UUID=abc-123 /opt/logs xfs defaults 0 2
# get UUID (use instead of /dev path)
$ blkid /dev/sdb1

# test fstab before reboot!
$ mount -a
Use UUID, not /dev/sdX. Device names can change on reboot. UUIDs are stable. Always test with mount -a before rebooting.
Slide 6 — Theory

LVM — Logical Volume Manager

The 3-layer stack
LOGICAL VOLUMES (what you use)
lv-root
20GB
lv-var
40GB
lv-data
80GB
↕
VOLUME GROUP (pool)
vg-main — 200GB total
↕
PHYSICAL VOLUMES (real disks)
/dev/sdb
100GB
/dev/sdc
100GB
↕
Physical Disk
Physical Disk
# 1. create physical volume
$ pvcreate /dev/sdb
$ pvdisplay

# 2. create volume group
$ vgcreate vg-main /dev/sdb
$ vgdisplay

# 3. create logical volume (40GB)
$ lvcreate -L 40G -n lv-data vg-main

# 4. format and mount
$ mkfs.ext4 /dev/vg-main/lv-data
$ mount /dev/vg-main/lv-data /opt/data
Think of LVM as virtual partitions. PV = physical disk, VG = a pool of storage, LV = the "partition" you actually use. Resize without rebooting.
Slide 7 — Theory

LVM — Online Resize

# scenario: /var is running out of space
$ df -h /var
Filesystem Size Used Avail Use%
/dev/vg-main/lv-var 40G 38G 1.2G 97%

# check available space in VG
$ vgdisplay vg-main | grep Free
Free PE / Size 1280 / 5.00 GiB

# extend by 5GB — NO UMOUNT NEEDED
$ lvextend -L +5G /dev/vg-main/lv-var

# resize filesystem to fill new space
$ resize2fs /dev/vg-main/lv-var # ext4
# or: xfs_growfs /var # xfs

# verify
$ df -h /var
/dev/vg-main/lv-var 45G 38G 6.2G 86%
Traditional disk vs LVM
Operation Traditional LVM
Grow partition Unmount + tools Online, no umount
Span 2 disks RAID or impossible vgextend + lvextend
Snapshot Not available lvcreate --snapshot
Move data Manual copy pvmove (live)
Add a new disk to existing VG
# hot-add new disk /dev/sdc
$ pvcreate /dev/sdc
$ vgextend vg-main /dev/sdc
# VG now has more free space
# extend any LV as needed

Expression Meaning

30 6 * * 1-5 Weekdays at 06:30
System-wide cron — /etc/cron.d/

# user field is required here
*/5 * * * * www-data /opt/app/check.sh

# also check /etc/cron.daily/ etc
$ ls /etc/cron.{hourly,daily,weekly,monthly}/
Slide 9 — Theory

systemd timer — Modern Scheduling

Two unit files needed
# /etc/systemd/system/backup.service
[Unit]
Description=Daily backup job

[Service]
Type=oneshot
ExecStart=/opt/backup.sh
User=backup
# /etc/systemd/system/backup.timer
[Unit]
Description=Run backup daily

[Timer]
OnCalendar=*-*-* 02:00:00 # daily 2am
Persistent=true # catch missed

[Install]
WantedBy=timers.target
# enable and start the timer
$ systemctl daemon-reload
$ systemctl enable --now backup.timer

# list all active timers
$ systemctl list-timers

# check logs — this is the big advantage
$ journalctl -u backup.service
$ journalctl -u backup.service --since "1 week ago"

# run manually to test
$ systemctl start backup.service
cron vs systemd timer
cron systemd timer
Logging Manual/syslog journalctl built-in
Missed runs Silently skipped Persistent=true
Dependencies None After=, Wants=
Syntax Simpler More verbose
Slide 10 — Real-world example

Example: /var full → expand online

Scenario — 3am alert: /var at 97%

Without LVM, you'd need to: schedule downtime, boot from live CD, resize partition, fsck, reboot. With LVM — zero downtime.

1 Alert fires: /var at 97% capacity
2 Check: VG has 5GB free → vgdisplay
3 lvextend -L +5G while /var is mounted
4 resize2fs to fill the new space
5 /var is now 45GB — no downtime, zero restarts
# full flow — under 2 minutes
$ df -h /var
/dev/vg-main/lv-var 40G 38.8G 774M 98% /var

$ vgs vg-main
VG #PV #LV VFree
vg-main 2 4 5.00g

$ lvextend -L +5G /dev/vg-main/lv-var
Logical volume lv-var successfully resized

$ resize2fs /dev/vg-main/lv-var
Filesystem on lv-var is now 11796480 (4k) blocks

$ df -h /var
/dev/vg-main/lv-var 45G 38.8G 5.2G 88% /var
Shortcut: lvextend -r -L +5G — the -r flag runs resize2fs automatically. One command does both steps.
Slide 11 — Real-world examples

Examples: Pinning & Timers

Version pinning nginx on production

Your app relies on nginx 1.24 behavior. A junior admin runs apt upgrade and nginx jumps to 1.26 — breaking a rewrite rule.

# pin BEFORE first unattended-upgrade runs
$ apt-mark hold nginx nginx-common

# verify hold is active
$ apt-mark showhold
nginx
nginx-common

# apt upgrade now skips nginx
$ apt upgrade
The following packages have been kept back:
nginx nginx-common
systemd timer: better debug than cron

Cron ran your backup script — did it succeed? With cron you check a log file manually. With systemd timer:

# exact status of last run
$ systemctl status backup.service
Active: inactive (dead)
Process: 4821 ExecStart=/opt/backup.sh
Main PID: 4821 (code=exited, status=0/SUCCESS)

# full output with timestamps
$ journalctl -u backup.service -n 30
May 02 02:00:01 srv01 backup.sh: Backup complete
May 02 02:00:01 srv01 systemd: backup.service: Deactivated

# next scheduled run
$ systemctl list-timers backup.timer

Lab Exercises

Cron job — timestamp every minute

Slide 13 — Summary

Key Takeaways

Pin before you upgrade. Version holds are free. Unplanned package upgrades in production are not. Make pinning a default habit for critical services.

LVM is the standard. Any server that might need more disk space should use LVM. Resizing online is the difference between a 2-minute fix and a maintenance window.

UUID in fstab, always. /dev/sdb can become /dev/sdc after a reboot. UUIDs never change. A bad fstab entry can prevent boot.

systemd timer for new work. When writing new scheduled tasks, prefer systemd timers. journalctl integration makes debugging 10x easier than reading syslog.

Commands to memorize
apt-mark hold apt show dpkg -L lvcreate lvextend -r vgdisplay resize2fs lsblk blkid mount -a crontab -e systemctl list-timers journalctl -u
4 things that break systems:
1. apt upgrade without pinning critical services
2. /dev/sdX in fstab instead of UUID
3. No mount -a test before reboot
4. Cron output going to /dev/null — errors silently lost
